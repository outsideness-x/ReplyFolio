# Безопасность ReplyFolio

Это описание реализованных границ и процедуры эксплуатации. Облачные проекты ещё не созданы; код и локальные SQL проверены, production-конфигурация и внешние сервисы пока не проверены. Абсолютную невозможность взлома обещать нельзя.

## Границы доверия

Недоверенные стороны: посетитель, outsider Auth identity, произвольные browser JWT/UUID, другой origin, повтор запроса, вход без MFA, подмена OAuth callback. Доверенные администраторы: владелец Supabase, Cloudflare и Meta с серверными ключами; компрометация их доступа выходит за пределы защиты только интерфейсом.

Закрытый список хранится в private.team_invites, не в Git или JavaScript. Email проверяется перед определением доступа; приглашение закрепляется за user ID и не передаётся автоматически другому аккаунту с тем же email. Изменение email прекращает доступ. Роль owner проверяется по текущему приглашению и membership.

## Реализованные меры

- Одноразовый email OTP, Turnstile, ограничения запросов по HMAC IP/email и количества попыток.
- Обязательный TOTP MFA; доверенный factor ID закреплён, дополнительный фактор из публичного Auth не подменяет его. Восстановление не сводится к новому письму.
- Непрозрачная случайная cookie __Host-rf-session: HttpOnly, Secure, SameSite=Strict, Path=/, без Domain. В базе только её хеш.
- JWT/refresh tokens находятся на сервере, AES-GCM ключ отдельно от ключа Instagram; шифрование привязано к session ID.
- TTL до 12 часов, тайм-аут 30 минут без backend-запросов, до трёх действующих серверных сессий.
- Подписанный proxy с одноразовым nonce, Origin/Fetch Metadata проверкой, whitelist маршрутов, 64KB лимитом и тайм-аутом upstream.
- Прямые browser grants к таблицам/RPC закрыты. RLS дополнительно связывает команду, AAL2 и утверждённый Auth session_id.
- Сервер проверяет workspace для чтения, изменения, выгрузки и материалов. Подключение/отключение Instagram требует owner и MFA не старше пяти минут.
- Одноразовый OAuth state с отдельной cookie browser proof, проверкой активной сессии, текущих прав и закреплённого фактора. Подмена другим Instagram ID запрещена.
- CSP, запрет framing, HSTS, no-referrer и запрет кеширования API. React отображает пользовательский текст без HTML-инъекции.
- Meta webhook подписан; worker защищён независимым secret. Private audit не содержит email, токенов и переписки. Истёкшие записи очищает Cron.

HttpOnly уменьшает возможность извлечь cookie через JavaScript, но XSS может выполнять действия из уже открытой сессии. MFA не защищает от компрометации устройства или административных ключей. Следите за зависимостями, устройствами и доступом к облачным консолям.

## Отзыв доступа

Администратор базы после проверки пользователя выполняет запрос с его реальным UUID:

```sql
begin;
update private.team_invites set enabled=false where claimed_user_id='AUTH_USER_UUID';
update private.web_sessions set revoked=true where user_id='AUTH_USER_UUID';
delete from private.oauth_states where user_id='AUTH_USER_UUID';
commit;
```

Это блокирует кабинет даже при остающемся Auth JWT. Затем отзовите соответствующие Auth sessions через admin tooling. Если потерян доступ владельца к устройству, отзовите также разрешение приложения в Instagram/Meta при необходимости. Не удаляйте бизнес-данные как побочный эффект отзыва входа.

## Потеря MFA и восстановление

Нет email-only reset и автоматического сброса factor ID. Администратор с отдельным защищённым доступом к Supabase проверяет личность вне потерянного email/устройства.

1. Отключите приглашение и отзовите все server/Auth sessions пользователя.
2. Через Auth admin удалите утраченные факторы. Не выбирайте произвольный недавно добавленный фактор.
3. Проверьте, что Auth user UUID прежний и email подтверждён; не переносите claimed_user_id автоматически.
4. Очистите trusted_factor_id только после проверки личности и удаления старых факторов, затем разрешите приглашение.
5. Пользователь проходит новый email-код и enrollment MFA. Проверьте audit и доступ.

Для первичного входа используйте ещё не зарегистрированную в Auth командную identity. Если уже есть verified factor вне доверенной процедуры ReplyFolio, приложение намеренно закрывает вход до проверки администратора.

## Секреты и аварийная ротация

Раздельные секреты: gateway, rate-limit HMAC, sessions AES, Instagram AES, worker, Meta и email. Не передавайте их в VITE_* и не публикуйте логи/дампы.

При утечке Auth/session ключей сначала отзовите server/Auth sessions; смена SESSION_ENCRYPTION_KEY делает прежние ciphertext нечитаемыми и требует нового входа. При смене Instagram encryption key заранее предусмотрите безопасное повторное подключение; старые токены без ключа не восстановить. Gateway secret меняется одновременно в Pages и Edge; промежуточное несовпадение должно закрывать доступ.

Потеря backup вместе с ключом даёт доступ к данным. Храните их отдельно, ограничьте участников облачных проектов и защитите admin accounts MFA. Не добавляйте production-секреты в preview deployments.

## Подтверждение

tests/team-security.test.ts выполняет миграции и проверяет grants, RLS, outsider, email/user ID binding, MFA factor pinning, Auth session ID, rate/replay и OAuth после отзыва/понижения прав. tests/gateway.test.ts проверяет CSRF, cookie parsing, подпись и маршрут proxy. e2e/access.spec.ts проверяет порядок экранов и отсутствие чтения данных outsider.

После deploy требуется отдельная проверка настоящего email, TOTP, Turnstile, cookie flags, headers, logout/revocation, прямого Edge запроса и Meta callback. Успешный локальный тест не подтверждает настройки провайдера.
